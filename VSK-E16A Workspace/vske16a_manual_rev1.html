1.Introduction

The VSK-E16A ("ExVSKa") is a 16-bit CISC-like virtual machine, and the newest member of the Virtual System Komputer (VSK) family. It implements a flat 64K-word memory space, sixteen general-purpose registers, a condition flag register, a descending hardware stack, and — new to this machine — a hardware interrupt line and a stack-based port-mapped I/O (PMIO) subsystem for talking to virtual peripherals such as disk.

This manual documents the VSK-E16A instruction set, memory layout, register file, interrupt model (both software and hardware), the PMIO subsystem, and the surrounding tooling (pre-run shell, live in-execution debug shell, and the debugger GUI).

Scope note This document describes the VSK-E16A as implemented in the reference emulator. Some behaviours (e.g. the bit-flopper, triple-fault handling, exact debugger performance tricks) are emulator features rather than strictly architectural guarantees, and are called out where relevant.

2.Relation to VSK-16A

VSK-E16A is described by its own source as "a copy of the VSK-16A — adds hardware interrupts and PMIO." The "E" stands for extended. It shares VSK-16A's general shape (16-bit words, 16 general-purpose registers, CISC-like variable-length instructions, the same assembler directive syntax) but is a genuinely different machine with a different opcode table and several removed subsystems. This manual should not be assumed to describe VSK-16A, and vice versa — treat them as siblings, not versions of one machine.

3.Architecture Overview

Execution is a fetch–decode–execute loop, structurally the same as VSK-16A: every cycle the CPU reads the word at IP, advances IP, and dispatches on it via the microcode table. A zero word is treated as padding and skipped. Instruction operands are pulled lazily by each handler rather than decoded up front, so instruction length is opcode-defined.

→
IP += 1 (mod 0x10000)
→
Check iF / HWI
→
Lookup opcode
→
Execute handler
→
Loop

One structural change from VSK-16A: IP is now masked to 16 bits on every increment inside the fetch primitive itself, rather than only being corrected after the fact at the top of the fetch loop. The fetch loop still carries its own wraparound guard as a second line of defence, so in practice IP cannot be observed out of the 0x0000–0xFFFF range at any point software could inspect it.

Fault handling

Every instruction dispatch is wrapped in a guarded call. If a handler raises one of the VM's typed exceptions (bad register index, stack over/underflow, out-of-range jump target, PMIO stack over/underflow, unmapped hardware port, etc.), the CPU does not crash the process. Instead it:

  • Maps the exception type to a small numeric fault code.
  • Stores the fault code in R13 and the faulting IP in R14.
  • Zeroes video memory from 0xF101 through 0xFFFF.
  • Clears the PMIO stack entirely.
  • Redirects IP to the handler address stored in Memory[0x00FF] (the fault vector).
  • Starts a 10-second window after which the fault-trapped state automatically clears if nothing else goes wrong — see Interrupts & Faults.
  • Resumes the fetch loop from there.

4.Memory Map

Memory is a flat array of 216 (65,536) words, addressed 0x0000–0xFFFF.

0x0000 – 0x08FF

0xF100 – 0xFFFF

No more keyboard buffer VSK-16A reserved 0xF000–0xF09A for a polled keyboard buffer. VSK-E16A has no such region — that whole address range is ordinary general-purpose memory now. Keyboard input arrives exclusively through the hardware interrupt mechanism described in Hardware Interrupts.
Stack bounds & MOVSP The stack grows down from its starting address. PUSH decrements the stack pointer before writing; POP reads then increments. Every push/pop/call/ret checks the resulting stack pointer against 0x0000–0xFFFF and raises StackOverflow (underflowed below zero) or StackUnderflow (grew past 0xFFFF). The stack pointer can be set directly with MOVSP, which BIOS/OS code is expected to use to establish its own stack region.

5.Registers & Flags

R0–R15general purpose

16 general-purpose 16-bit registers, referenced in assembly as r0 through r15. Two carry conventional meaning:

  • R13 — last fault code (written automatically on a trapped exception)
  • R14 — faulting instruction pointer (written automatically on a trapped exception)
IPhardware reserved

Instruction pointer. Points at the next word to fetch. Masked to 16 bits on every increment.

SP (stack)hardware reserved

Stack pointer, initialised to 0x0000. Decrements on push, increments on pop. Settable directly via MOVSP.

FLAGShardware reserved

Comparison flag, set by CMP and reset by CLF:

0 no comparison performed yet
1 operands were equal (EQ)
2 first operand was greater (HI)
3 first operand was less (LO)
0xFFFF explicitly cleared via CLF
iF (interrupt flag)hardware reserved — new

A single hardware-reserved flag controlling whether the CPU checks for pending hardware interrupts on each cycle. 0 = hardware interrupts disabled, 1 = enabled. Set and cleared via EHI and DHI respectively. See Hardware Interrupts.

Hardware-reserved pseudo-registersMOVFS source IDs

MOVFS reads one of the hardware-reserved registers into a general-purpose register via a fixed numeric ID. These IDs exist only as immediate operands to MOVFS.

Removed opcodes KEY, DREAD, and DWRITE do not exist in VSK-E16A. Their old opcode numbers were reassigned to DHI, EHI, and IN respectively — a VSK-16A binary image containing those instructions will not run correctly (or at all) on VSK-E16A, since the same numeric opcodes now mean something entirely different.

9.Interrupts & Faults

Software interrupts

INT requires its vector to fall inside the IVT (0x0000–0x00FF); the handler address is read from that slot, and execution jumps there after pushing a return address. A vector outside the IVT raises InvalidInterrupt.

Fault trapping

On trap: R13 receives the fault code, R14 receives the faulting instruction pointer, video memory from 0xF101 through 0xFFFF is zeroed, the PMIO stack is cleared entirely, and IP is redirected to the handler address stored in Memory[0x00FF].

Wider fault-zeroing than VSK-16A Because there's only one video region now, the fault handler's memory-clear sweep covers the entire thing (0xF101–0xFFFF), unlike VSK-16A Rev 7.0 where a fault only zeroed the legacy region and left the extended region untouched.
Triple fault window is now time-limited In VSK-16A, once the machine entered a trapped fault state, a second fault during that state was unconditionally treated as a triple fault. VSK-E16A adds a 10-second timer: if no second fault occurs within 10 seconds of the first, the trapped state automatically clears itself in the background. A second fault that lands within that 10-second window still triggers a triple fault exactly as before. CLF can also clear the trapped state early and manually.

10.Hardware Interrupts

VSK-E16A adds a genuine hardware interrupt line, distinct from the software INT instruction. It exists specifically to let the CPU react to keyboard input without a program having to block waiting for it.

The interrupt flag (iF)

A single hardware-reserved bit, toggled by EHI (enable, sets iF=1) and DHI (disable, sets iF=0). Every cycle, if iF is set, the fetch loop polls for a pending key press before executing the next instruction.

Delivery mechanism

When a key is detected while iF is set, the CPU:

  1. Pushes the key's raw code onto the PMIO stack (not the ordinary call stack).
  2. Decrements the stack pointer and pushes the current IP onto the ordinary call stack, the same way a software CALL or INT would — but with one difference: if the stack pointer would go out of bounds, the hardware interrupt handler silently restores the stack pointer and returns early rather than raising a fault. Because this delivery path runs outside Instruct()'s guarded dispatch, a general-protection-style fault genuinely cannot be raised from here.
  3. Sets IP to the address stored at the fixed keyboard interrupt vector, Memory[0x00EF].

Handler code at that address is responsible for reading the key back off the PMIO stack (typically via IN) and returning with RET, the same as any other interrupt handler would.

Minimal keyboard-driven idle loop
; install a handler at 0x00EF beforehand, e.g.:
; mov [0x00EF], KEY_HANDLER

ehi              ; enable hardware interrupts

idle:
  shlt           ; sleep until a key arrives
  jmp idle       ; handler already ran and returned by the time we get here

KEY_HANDLER:
  in r1          ; pop the key code off the PMIO stack into r1
  ; ... handle the key in r1 ...
  ret

This is the idiomatic VSK-E16A pattern for input-driven code: enable hardware interrupts once, then use SHLT to idle cheaply rather than busy-polling.

Polling cadence outside the interrupt system Independent of iF, the fetch loop checks for the host P (pause) and F12 (live shell) keys roughly every 16,384 cycles as a low-overhead background check. This is an emulator/tooling convenience, not part of the hardware interrupt model itself, and is not something guest software can observe or rely on.

11.Port-Mapped I/O (PMIO)

PMIO is VSK-E16A's mechanism for talking to virtual hardware devices — currently just disk, but the port model is general. Unlike VSK-16A's dedicated DREAD/DWRITE opcodes, all device communication goes through a shared 256-entry LIFO stack and two generic instructions, IN and OUT.

The PMIO stack

A single stack, capacity 256 words, shared by all ports and by hardware interrupt delivery (see above). IN pops from it into a register; OUT in non-notify mode pushes a raw value onto it directly. It is entirely separate from the CPU's own call/data stack (SP).

Shared, not per-device There is exactly one PMIO stack for the whole machine — it is not partitioned per port. Device protocols (like the disk protocol below) rely on pushing/popping values in a specific order and trust that nothing else interleaves with them in between. A hardware interrupt firing mid-sequence also pushes onto this same stack, so software driving a multi-step PMIO protocol should keep interrupts disabled (DHI) for the duration if correctness matters.

OUT calling convention

OUT takes no encoded operands; it reads three registers:

RegisterMeaning
R1Target port number
R2Value (used only when not notifying)
R3Notify flag — truthy selects device-notify mode, falsy selects raw-push mode
  • Notify mode (R3 truthy): looks up R1 in the port map and invokes that device's driver directly. R2 is ignored in this mode. Raises PMIO_HardwareIOPortNotFound if the port has no registered device.
  • Raw-push mode (R3 falsy): pushes R2 onto the PMIO stack as-is, without involving any device. Raises PMIO_StackOverFlow if the stack is already at capacity.

IN calling convention

IN r pops the top of the PMIO stack into register r. Raises PMIO_StackUnderFlow if the stack is empty.

Port map

PortDevice
1Mass storage (disk)

Before notifying port 1, software must push a mode word and an address word onto the PMIO stack (and, for writes, a value word), in this exact order — the driver pops them in reverse:

; read one word from disk address 0x0010, leave the result in r5

mov r3, 0        ; raw push, no notify

Push order matters: the driver pops mode first, then address, so address must be pushed before mode. Get this backwards and the driver reads the wrong values without any error, since OUT's raw-push mode has no way to know what a value is "supposed" to mean.

Raw disk I/O detail Underneath the PMIO protocol, disk reads/writes are plain 2-byte big-endian word seeks against the disk image file. A short read or any other low-level I/O failure raises DiskIO (fault code 300), same as VSK-16A.

12.Video Output

VSK-E16A has a single video region and a single rendering path — there is no mode flag and no legacy fallback. VOUT always does the following:

  1. Scans forward from 0xF100 toward 0xFFFF, stopping at the first zero byte encountered.
  2. Builds an in-memory frame buffer as it scans: printable bytes (0–127) are appended as characters; reserved byte values are appended as colour-switch escape codes (table below).
  3. Performs a single flush at the end: one ANSI escape sequence to clear/reset the terminal, immediately followed by writing the entire assembled frame in one shot.

Because the terminal is only touched twice per VOUT call (clear, then write) rather than once per byte, this does not flicker. If the scan pointer runs past 0xFFFF without hitting a terminating zero, it wraps to 0x0000 and raises MMIO_OutOfBounds.

The code table itself is unchanged from VSK-16A Rev 7.0's extended mode; what's different is that this is now the only mode, with no flag to select or fall back from.

13.Boot Sequence

Startup gate

On launch, the VM checks whether Ctrl is being held:

  • Ctrl held — the interactive pre-run shell opens.
  • Ctrl not held — the VM loads the default hard-disk image into memory immediately. If P is also being held, it then pauses with a message and waits for Enter before continuing — but note that the image has already been loaded into memory by this point, unlike the pause behaviour in VSK-16A, which deferred the load itself until after the pause was released.

BIOS loading

The BIOS image is a .rom file. If missing, the VM raises CriticalError(55) and halts with a "VMBIOS Not Present" message. When present, it's copied into memory starting at 0x0000 up to (and including) 0x08FF, preserving whatever convention the BIOS itself uses at 0x0900 and beyond.

No confirmed VBPT/legacy-signature behaviour for VSK-E16A VSK-16A's reference BIOS validated a VSK Boot Protocol Table (VBPT) at 0x1100 and fell back to a legacy signature check at 0x0900. The VSK-E16A emulator still respects 0x0900 as a BIOS-load boundary (the same END = 0x0900-1 convention), which is consistent with a VBPT-style boot table still being in use at the BIOS level — but no VSK-E16A-specific BIOS source has been reviewed for this manual, and legacy 255-mode fallback specifically cannot apply anymore since that display mode no longer exists. Treat any VBPT details from the VSK-16A manual as unconfirmed for VSK-E16A until a VSK-E16A BIOS source is available.

BIOS compatibility shim

Same mechanism as VSK-16A: the shell's enabcsm command patches the first 10 words of the loaded BIOS image with a stub (MOV R1, 0xEFFF / MOVSP R1 / JMP 0x0600) for older BIOS images that never set up their own stack. As before, this unconditionally overwrites the first 10 words of whatever is loaded, so it will break a BIOS that already sets up its own stack at a conflicting address.

15.Live Running Shell (F12)

New in VSK-E16A: a second, entirely separate shell that can be entered while the VM is executing, by pressing F12. The fetch loop checks for this roughly every 16,384 cycles. Entering it clears the screen and takes over the terminal — the VM's own execution is effectively suspended (the Python thread is inside this input loop) until the shell is exited.

16.Debugger GUI

A read-only Tkinter debugger window runs alongside the VM in a background thread, retitled "VSK-E16A Debugger" and widened to accommodate new telemetry. As before, it never mutates VM state on its own — it only polls and displays it on a timer (default every 250 ms).

  • Registers panel — all 16 general-purpose registers, plus IP, SP, FLAGS, the new IF readout, the top of the PMIO stack, current cycle count, VM memory usage, host CPU usage, and a new guest clock-speed readout in kHz (measured live by a background thread that samples cycles-per-second once per second).
  • Memory panel — a scrollable hex + ASCII dump of the full 64K-word address space. The line containing the current IP is highlighted in grey, and new in this revision, the exact word at IP within that line is additionally highlighted in red, distinguishing the specific instruction word from the rest of its 16-word row.
  • Live decompile toggle — new: an opt-in checkbox that, when enabled, appends a best-effort disassembly of each visible memory row using the same opcode table the assembler encodes with. It's a heuristic view (it can't reliably distinguish code from data, and does not attempt to fully resolve variable-length operands like LOAD strings), only computed for rows currently on screen, and does not claim correctness on data regions.
Performance notes Two changes were made purely for responsiveness on larger/longer-running programs: the "words used" percentage is now maintained as a running count refreshed on a slow 2-second background cycle rather than rescanned from all 65,536 words every UI tick, and memory-view redraws are limited to whatever rows are actually scrolled into view rather than reformatting all ~4,096 rows every tick. Neither changes what the debugger reports, only how cheaply it computes it.
